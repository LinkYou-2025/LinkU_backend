작업 목표:
- 현재 브랜치의 변경사항을 마무리하고, 품질 점검과 커밋 준비를 수행한다.

입력:
- $ARGUMENTS 에 작업 범위, 완료 기준, 커밋 전략이 들어올 수 있다.

반드시 수행할 절차:
1. 현재 변경 파일과 git diff를 확인한다.
2. 작업 목적을 3줄 이내로 요약한다.
3. 코드 품질 관점에서 개선 포인트를 찾는다. 단, 불필요한 대규모 리팩토링은 피한다.
4. simplify 방식으로 가독성, 중복, 네이밍, 예외처리, 테스트 누락 여부를 점검한다.
5. Kotlin 프로젝트라면 `ktlintCheck` 실행을 우선 제안하거나 실행한다.
6. `ktlintFormat` 은 자동 실행하지 않는다.
7. 테스트/빌드/린트 결과를 요약한다.
8. 변경사항을 논리 단위로 나눠 순차 커밋 계획을 세운다.
9. 각 커밋에 대해 커밋 메시지 초안을 제안한다.
10. 사용자가 승인하면 커밋만 수행하고 push 는 하지 않는다.

제약:
- 사용자의 명시적 승인 없이 commit 하지 않는다.
- 절대 push 하지 않는다.
- 포맷 변경만 대량으로 발생하는 수정은 피한다.

커밋 메시지 규칙:
- 팀 컨벤션이 있으면 그 규칙을 따른다.
- 없으면 `type(scope): summary` 형식을 사용한다.

출력 형식:
- "작업 요약"
- "품질 점검 결과"
- "커밋 계획"
- "승인 필요 항목"
